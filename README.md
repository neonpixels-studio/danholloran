# danholloran.me

Personal blog and portfolio for Dan Holloran — full-stack developer and photographer based in Reno, NV.

## Development Setup

### Prerequisites

- [Node.js](https://nodejs.org/) v26+ (use [nvm](https://github.com/nvm-sh/nvm): `nvm use`)
- [npm](https://www.npmjs.com/) v11+
- [gitleaks](https://github.com/gitleaks/gitleaks#installing) (optional, `brew install gitleaks`): the pre-commit hook scans staged changes for secrets and skips with a warning when it is missing. CI always scans pull requests and pushes to `main`.

### Getting Started

1. Clone the repository:

   ```sh
   git clone https://github.com/neonpixels-studio/danholloran.git
   cd danholloran-me
   ```

2. Install the correct Node version:

   ```sh
   nvm use
   ```

3. Install dependencies:

   ```sh
   npm install
   ```

4. Start the development server:

   ```sh
   npm run dev
   ```

### Environment variables (dotenvx)

Production build secrets (the Sentry source map upload token first) live in `.env.production`, committed encrypted with [dotenvx](https://dotenvx.com). Netlify holds one value, `DOTENV_PRIVATE_KEY_PRODUCTION` (delete any separate `SENTRY_*` variables there: dotenvx never overrides a variable that is already set, so a leftover would silently shadow the encrypted value), and the Production deploy context builds with `npm run build:production`, which decrypts the file with `dotenvx run --strict`. `--strict` fails the build when the key is missing instead of building without the values. Deploy Previews, branch deploys, CI, the dependency audit, and Lighthouse use the plain `npm run build` and never need the key.

- **Add or change a value:** `npx dotenvx set KEY value -f .env.production`, which encrypts it (start the command with a space, with `HISTCONTROL=ignorespace`, to keep the value out of shell history). Add the name to `.env.example` with a comment saying what it is and where the value comes from; a test fails if the two files declare different names or if any value is not encrypted. The pre-commit hook runs `npx dotenvx ext precommit`, which refuses a commit that stages plaintext in a tracked `.env*` file.
- **Where the private key lives:** in the gitignored `.env.keys` on the maintainer's machine and in the Netlify environment as `DOTENV_PRIVATE_KEY_PRODUCTION` (Production context, Builds scope only, so Functions can never read it; mark it "Contains secret values"). It is never committed.
- **Rotate the key:** dotenvx 2 has no rotate command, and `encrypt` reuses the key pair it finds. With the old key in `.env.keys`, run `npx dotenvx decrypt -f .env.production`, delete the `DOTENV_PUBLIC_KEY_PRODUCTION` line from `.env.production` and the old entry from `.env.keys`, then `npx dotenvx encrypt -f .env.production`, which generates a new pair. Confirm with `npx dotenvx keypair -f .env.production` that the public key changed. Commit the re-encrypted file (never the decrypted one), then update `DOTENV_PRIVATE_KEY_PRODUCTION` in Netlify before the next production deploy. Rotating does not change the underlying secrets, so also revoke any credential that was exposed.

### Responsive post images

Post cover images under `public/images/posts/` (`.jpg`/`.jpeg`/`.png`, directly
in that directory — see `isVariantEligible` in `responsiveImage.ts`) are served
through a shared `ResponsiveImage.vue` component that renders a `<picture>`
with avif/webp variants sized for their context (small list/card thumbnails
vs. the larger single-post hero). A cover image outside that set (a different
format/location) renders as a plain `<img>` instead — a `<picture>`'s
`<source>` does not fall back to the next one on a 404, so `ResponsiveImage`
only ever points one at variant urls it's sure were generated.

The variant files are generated by [`sharp`](https://sharp.pixelplumbing.com/)
and **committed** to `public/image-variants/`, so builds never encode
images (encoding ~330 images on every Netlify deploy took the build past 10
minutes). Each source image's content fingerprint is recorded in
`.vitepress/data/imageVariantsManifest.json`; only images whose fingerprint
changed get re-encoded, and variants for deleted images are pruned.

- **Pull requests:** the Image Variants GitHub Action
  (`.github/workflows/image-variants.yml`) runs on any PR touching
  `public/images/posts/`, commits the new variants back to the PR branch,
  and re-dispatches the required `ci`/`lighthouse` checks (pushes made with
  the Action's own token don't trigger workflows on their own). Nothing to do
  by hand, including for posts opened by automation.
- **Locally:** `npm run dev` runs `npm run images` first. Run `npm run images`
  directly to regenerate without starting the dev server.
- **Builds:** `npm run build` only verifies that every post image has current
  variants and fails with the list of stale images otherwise. Netlify deploy
  previews are skipped (via `netlify-ignore.sh`) while a PR's variants are
  still pending from the Action; production always builds.

Adding a post image while `npm run dev` is already running needs a
dev-server restart (or `npm run images`) before its `<picture>` has real
variants.

### Resume PDF

The downloadable resume (`public/dan_holloran_resume.pdf`, linked from
`/resume`) is a static export of the live resume data — `resume.ts` plus
everything it reads from (`skills.ts`, `past-locations.json`,
`theme/utils/constants.ts`, `data/location.json`) — kept in sync by a human
re-running the Claude skill `resume-pdf-export`. It isn't regenerated
automatically, since that skill isn't available in CI. To guard against the
PDF silently going stale, a combined content fingerprint of those source
files, the PDF's own fingerprint, and the "years of experience" value
computed from the current date (which no file stores, so a year rollover
alone can go stale) are recorded in `.vitepress/data/resumePdfManifest.json`:

1. Edit `resume.ts` (or one of the files it reads from).
2. Re-run the `resume-pdf-export` skill to regenerate the PDF.
3. Run `npm run resume:pdf:sync` to record the new state.
4. Commit the resume source file(s), the PDF, and
   `resumePdfManifest.json` together.

If the source data changed but the PDF's bytes didn't, `resume:pdf:sync`
refuses (the export skill most likely never actually ran) unless you pass
`npm run resume:pdf:sync --force` (or `npm run resume:pdf:sync -- --force`;
both work, since the script also reads the `npm_config_force` variable npm
sets when it claims a bare `--force` for itself).

`npm run build` runs `npm run resume:pdf:check` first and fails with a fix-it
message if anything is stale or missing; the same check also runs against
the real committed files in `resumePdfManifest.test.ts`, so `npm run
test:ci` (part of the `ci` GitHub Action) catches drift on every PR, not
just at deploy time. It intentionally does **not** run at `vitepress
dev`/`preview` config-load time — nothing regenerates the PDF the way `npm
run images` does for post images, so that would just break local dev the
moment the resume data changes.

### Sweep commits: the `Skip-Modified` trailer

The sitemap `lastmod` date and the post "last modified" date come from git
history (`gitLastModified` in `.vitepress/theme/utils/gitLastModified.ts`).
A commit that carries the trailer `Skip-Modified: true` is ignored when
picking a file's last-modified date, so mechanical changes don't make every
post look freshly edited.

Add the trailer to any sweep commit that changes post files without changing
their content: Prettier runs, frontmatter migrations, description trims,
bulk renames. Git only reads trailers from the last paragraph of the message,
so keep it in the final block, with no blank line between it and any other
trailers:

```text
Trim post descriptions to 160 characters

Skip-Modified: true
Co-Authored-By: Name <name@example.com>
```

PRs are squash-merged, so the trailer must be in the final squash commit
message, not just on a branch commit. GitHub's default squash message
concatenates the branch commits, so edit it before merging and put
`Skip-Modified: true` in the last paragraph, in the same block as any
`Co-authored-by:` lines. Commits that touch more than 20 markdown
files are skipped automatically, but rely on the trailer for smaller sweeps.
If every commit for a file is skipped and the file has 50 or fewer commits,
its creation commit date is used instead; otherwise no git date is returned. Trailer parsing needs Git 2.22 or newer; on older Git the trailer is
silently ignored and only the 20-file threshold applies. The behavior is
pinned by `.vitepress/tests/utils/gitLastModified.test.ts`.

### Error reporting

Production builds report browser errors to [Sentry](https://sentry.io) with `@sentry/vue`, filtered and scrubbed by `@neon-pixels/sentry`. Errors only: no tracing, Session Replay, or session tracking, and no user info or cookies, so it does not depend on analytics consent. The SDK is a separate chunk loaded after the page has finished loading (`startErrorReporting.ts`), so it is not in the entry bundle and a failed load never breaks a page (errors thrown before it loads are not reported). The DSN is a public constant in `.vitepress/theme/utils/errorReporting.ts`, the Sentry ingest origin is allowed in `connect-src` in `public/_headers`, and the privacy page describes what is sent.

The Sentry environment comes from Netlify's `CONTEXT`, read at build time, so deploy previews report as `preview` and local builds as `development`.

#### Source maps (optional)

Builds always generate hidden source maps. They are uploaded to Sentry only when all three variables are set in the build environment (for example the Netlify environment):

| Variable            | Description                                            |
| ------------------- | ------------------------------------------------------ |
| `SENTRY_AUTH_TOKEN` | Sentry auth token with release/source map write access |
| `SENTRY_ORG`        | Sentry organization slug                               |
| `SENTRY_PROJECT`    | Sentry project slug                                    |

Without them the build still succeeds, uploads nothing, and logs `Source map upload skipped`. Either way every `.map` file is removed from the published output (checked by `npm run test:dist`).
